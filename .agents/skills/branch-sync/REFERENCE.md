## 一、智能体运行环境的 git 语义（沙箱 / 工具约束）

在受沙箱约束的智能体环境里，`git` 的行为与手敲终端**并不一致**。以下差异会直接导致误判，
建议按「所有 git 写操作与真值核对都走脚本 + 显式参数」的方式执行。

### 1.1 引用写入可能被静默虚拟化

部分沙箱会拦截 `refs/remotes/**` 的写入：`git fetch` 会正常打印
`old..new <分支> -> origin/<分支>`，但引用**实际没有落盘**。之后 `git rev-parse origin/<分支>`、
`git branch -r -v` 读到的都是陈旧值，极易误判成「远端分支被推坏 / 提交丢了」。

- **远端真值只信 `git ls-remote <remote>`**（该命令不写本地引用，不受影响）。
- **本地侧做净贡献甄别时，用本地分支对象而非 `origin/*`**：`git cherry -v <本地集成分支 tip> <源分支>`。
- 需要连续多个 git 操作时，用宿主语言的进程调用（如 Python `subprocess.run(['git', *args], cwd=...,
  capture_output=True, text=True, errors='replace')`），一次进程内串起来，避免逐条 shell 调用。

### 1.2 调用超时会向 git 发 SIGTERM

大 worktree（含构建产物时数万文件）的 `reset --hard` / `checkout` 磁盘 I/O 很慢。工具调用超时
会把 git 杀在中途，留下 `index.lock` 与成片的半删除文件（`git status` 满屏 ` D`），
现象是「卡住 / 跑了几分钟没结果」。

- 给足超时（如 `timeout=600`），并用脚本进程调用而非交互式 shell。
- 被中断后先删锁再重跑：`<worktree>/.git/worktrees/<name>/index.lock`。

### 1.3 精简 shell 环境可能缺 coreutils

部分工具的 shell shim 不含 coreutils（`rm` / `ls` / `cat` / `tail` / `head` / `date` 全部不可用）。
清理锁文件、枚举目录、删除临时文件请改用宿主语言（Python `os.remove` / `os.listdir`）。

### 1.4 跟踪引用丢失（`[gone]`）的修复

症状：`git status -sb` 显示 `## <分支>...origin/<分支> [gone]`，`git for-each-ref refs/remotes/`
返回空。这不是显示噪音——Git 认为远端分支已被删除，会诱使人去做错误的 prune / 重建。**必须修**。

> 注意：**任何 `git push`（包括「Everything up-to-date」的空推送）都可能清空
> `refs/remotes/*`**，所以不存在「修一次就永久好」的方案，每次推送后都要复核。

修复步骤（`git fetch` / `git update-ref` 在被拦截时**返回 0 但值不变**，不要依赖它们）：

1. 取远端真值：`git ls-remote <remote>`。
2. 先判断载体：跟踪引用可能存于 `.git/packed-refs`（无 loose 目录），也可能是 loose 文件
   `.git/refs/remotes/<remote>/<分支>`。**不要假定 packed-refs 一定存在**。
3. 用宿主语言直接写文件：
   - loose 形式：写入 **41 字节**（40 位 sha + `\n`），**必须以 ASCII 编码写入**——默认 UTF-8 在
     Windows 会写出 BOM，Git 虽容忍但 `git fsck` 会持续报 `trailingRefContent`。
   - packed 形式：改写 `.git/packed-refs` 中对应行的 sha（目标值取自 `ls-remote`）。
4. 验证：`git fsck --no-progress --connectivity-only` 不再有引用告警（只剩 dangling 对象，正常）；
   `git status -sb` 出现 `## <分支>...origin/<分支>`。
5. 多个 worktree 共用主仓库同一份 `packed-refs`，改一次全部生效。

> 附带收益：引用恢复后 `git branch -vv` 才会显示 `[origin/<分支>: ahead N]`——
> 引用丢失期间这个信息是完全隐藏的，容易漏掉未推送的提交。

## 二、强推前的净贡献复核与误覆盖抢救（硬性）

**`--force-with-lease` 不是安全网。** 它只保证「远端自你上次观察后没被改」，
**不保证远端没有你没看到的净贡献**：别人在你观察之后推了新提交时，lease 会取到新值、
判定为一致并放行，把那些提交从远端抹掉。

### 推送前（每次都要做）

1. **当场重新 `ls-remote` 取 lease**，禁止复用几分钟前的观察值。
2. 用该 sha 再算一次 `git cherry -v <集成分支> <远端sha>`；**有 `+` 说明远端有新活，
   先合入再推**。
3. 推送统一用**显式**形式（隐式形式在部分环境会报 `stale info`）：
   ```
   git push --force-with-lease=refs/heads/<分支>:<刚取到的远端sha> <remote> refs/heads/<分支>
   ```

### 误覆盖后的抢救

托管平台通常仍能按 sha 取回已变成悬空的提交（如 GitHub 的 `allowAnySHA1InWant`）：

1. `git fetch <remote> <被覆盖的完整sha>`；
2. 立刻钉住：`git update-ref refs/recovered/<分支>/<时间戳>-<sha> <sha>`；
3. `git cherry -v <集成分支> <sha>` 取出净贡献，按序 cherry-pick 回来。

**抢在 `gc` 之前做**，并把集成分支先推上去让它在远端重新可达——集成分支落地后，
抢救窗口立即关闭。

## 三、分叉场景的判定与人工处置

当「本地分支停在旧基线（其独有提交已被集成分支等价合入，`git cherry` 全为 `-`）」
而「远端同名分支基于新集成分支又有新提交」时，同步脚本会在 Tree-Diff Guard 阶段判定为
**Diverged 并报错拦截**。此时不要用 `-NoFetch` 之类的开关绕过（那会丢掉远端提交），正确处置：

1. `git cherry -v <集成分支> origin/<分支>`——`+` 行是远端净贡献；本地侧的 `-` 行说明已等价合入，
   可安全丢弃；
2. 在以集成分支检出的工作区里，按序 cherry-pick 这些净提交，然后 `git push origin <集成分支>`；
3. 在分支所在 worktree 内 `git reset --hard <集成分支 tip>`；
4. 显式 lease 强推，lease 值取**远端旧 sha**。

## 四、多分支批量合入方法论

- **按 `committerdate` 全局排序后逐个 cherry-pick，不要按分支分组。** 多分支常改同一文件，
  按时间序能让「先做的改动」先落地，后续提交的补丁上下文更接近，冲突显著减少。
- **合入后必做「改动完整性校验」**：比较源提交与其落地提交的文件级 diff，抹掉 hunk 行号后
  逐行应一致；不一致说明有内容被吞。这比「无冲突」可靠得多。
- **`git cherry` 残留 `+` 不一定等于漏合**：因冲突解决或合入顺序导致 patch 变化时会误报。
  用下面的「已合入」判别法确认改动已完整落地即可：
  1. 先在集成分支按 subject 找同名提交；
  2. 只比较两个补丁的**增删行**（剥掉 `+++` / `---` / `@@` 与行首符号、`strip()` 后，
     算 `difflib.SequenceMatcher.ratio()`）；
  3. `ratio ≈ 1` 且文件清单一致 → 判定已合入；集成分支侧多出几行（并行分支引入的额外判据）
     说明是超集，更安全。
  - 整补丁（含上下文）比对会产生大量「差异」，几乎全是 hunk 上下文漂移，不要被它误导。

### 冲突取值约定

- 默认**取源分支（待合入）一侧**：源分支通常是较新的功能改动，集成分支的旧注释可能已过时。
- **例外**：上述默认只适用于「两侧是同一处改动的两种写法」。若两侧是**不同维度的改动**
  （例：一侧加了类型强转、另一侧加了判空条件），**必须两侧都保留**——先看完整 diff 理解语义
  再动手，不要只看冲突块。
- 解决后 `git add <文件>`，再 `GIT_EDITOR=true git cherry-pick --continue`（本地钩子会自动跑校验）。

## 五、生成物 / 资源文件的实体级冲突合并

带翻译资源、生成清单等「多条独立条目」的文件，cherry-pick 时常爆出上百个冲突块，
但绝大多数只是**位置/行号漂移**，语义内容本身没有冲突。

- **判定**：扫描每个冲突块，剥掉位置类属性（如 `line="\d+"`）后两侧是否逐行相同——是则为纯漂移。
- **解法**：以集成分支版本为底，把源分支**独有**的条目（按稳定标识去重，如 `<source>`）
  追加到同名分组（如 `<context>`）末尾。这样两侧新增内容都不丢，位置以集成分支为准
  （下次重新生成时会自动校正）。
- **合并后必须校验**：冲突标记为 0、文件能被对应解析器正常解析（如 `ElementTree.parse()`）、
  两侧的关键内容都能检索到；源语言资源文件应保持译文为空。

## 六、合后失败用例的基线判定

同步后跑测试出现失败时，**不要凭「改动面不相关」就判定为 flaky**，应先做一次**真基线**：

1. `git checkout --detach <合并前集成分支 tip>`；
2. 用增量编译（如 `sccache`）重建**仅受影响的测试目标**，跑失败用例——通常只需重编少量编译单元；
3. `git checkout <集成分支>` 回到同步后的 tip（分支指针从未移动，安全）；
4. 基线同样失败且断言一致 → 预存失败，与本次同步无关；基线通过 → 真回归，必须修。

反例（常见误判来源）：

- **不要用兄弟 worktree 的构建产物当基线**——那可能是几周前的旧 exe，跑出来的是假基线。
- **确认真实执行的测试集合**：测试运行器的「测试名」未必等于可执行文件名，一个可执行文件常被
  注册成多个测试名。用名字过滤时若一个都没匹配上，某些运行器仍**返回 0**，会伪装成通过；
  务必核对测试注册处并确认输出里真的「开始执行」了。
- **带参数的测试目标要用注册处抄来的参数**，不要自己拼——缺参数去加载需要独立 fixture 的套件，
  会表现为成片的「符号未定义」假失败甚至异常退出。
