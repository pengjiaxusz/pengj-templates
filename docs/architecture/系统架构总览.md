# 系统架构总览 架构规范

> **索引定位**：本文档对应 `docs/architecture/README.md` 全局系统架构第一行【权威规范】，
> 定义分层模板工具四件套（引擎 Rust + CLI clap + GUI Tauri 2/React + templates 运行时目录）
> 与整体生命周期（发现→依赖排序→合并渲染→生成/纳管/更新→manifest 驱动同步）的权威边界与约束。
> 下层细分文档（模板合并与渲染管线、受管块与 TOML 合并、Manifest 与同步更新等）均以本文为准展开。
> 本文档 200–400 行，聚焦架构约束而非 CLI 使用手册。

## 1. 定位与系统边界

- **核心定位**：本系统是一套**分层模板的生成 / 纳管 / 更新引擎**，
  将仓库模板按“层（layer）”组织——勾选所需层即按依赖拓扑合并渲染出可直接可用的新仓库，
  并在模板演进后以 `.pengj-templates.json` 哈希基线为依据一键同步到所有已生成项目，
  受管区间外用户内容 100% 保留。

- **边界划分**：

  - **本模块负责（In-Scope）**：

    - 层发现与元数据解析：
      扫描 `templates/<layer>/layer.toml`（字段 `name` / `description` / `depends` / `update_ignore`），
      自动发现无需注册；
      `Templates::list_layers` 与 `list_skills` 对外暴露层与技能清单，
      `file_count` 统计跳过 `layer.toml` 本身。

    - 依赖排序：
      `Templates::resolve_layers(selected)` 对选中层做 DFS 拓扑排序（先依赖后自身、已去重），
      环检测返回 `CoreError::CircularDependency`，未知层返回 `CoreError::UnknownLayer`。

    - `FileMap` 三桶分流：
      `FileMap { normal, concat, json }` ——
      普通文件后层覆盖前层（`BTreeMap::insert` 覆盖语义），
      `.gitignore` / `.gitattributes` 按 `ACCUMULATE_FILES` 累加拼接，
      `package.json` 按 `MERGE_JSON_FILES` 并集合并。
      技能文件按 `skill_name_of(rel)` 命中 `.agents/skills/<name>/…` 时
      查 `selected_skills(options)` 白名单（`options["skills"]` 缺失则全量，向后兼容）。

    - 模板渲染：
      `RenderContext { project_name, project_slug, year, layers, options }` 驱动 minijinja，
      `render_text` / `render_bytes` + `is_text`（前 8KB 无 NUL 即文本，二进制直通），
      占位符 `{{ project_name }}` / `{{ project_slug }}` / `{{ year }}` / `layers` / `options`，
      年份由 `chrono_lite_year`（`SystemTime` 粗算，无 `chrono` 依赖）提供。

    - 三流程：
      `generate` 空目录生成、`adopt_project` 存量纳管、`update_project` 增量同步，
      统一涵盖黑名单、结构化合并、受管块合并、冲突判定与报告
     （`GenerateReport` / `AdoptReport` / `UpdateReport` / `ConflictInfo`）。

    - Manifest 基线：
      `.pengj-templates.json` 持久化 `layers` / `options` / `files: sha256`，
      作为 `update` 时“未改→覆盖 / 已改无块→冲突跳过 / 有块→合并”的唯一判定依据，
      `sha256_hex` 基于 `sha2::Sha256`。

    - 受管块与结构化合并：
      `Html`（`<!-- -->`）/ `Hash`（`#`）/ `Slash`（`//`）三风格
      `PENGJ_TEMPLATE_START/END` 的提取 / 原位替换 / 追加（`block.rs`）；
      `.cargo/config.toml` 走 `toml_merge` 表级并集、键级去重、同键异值冲突跳过；
      `package.json` 依赖版本模板为准、脚本用户优先；
      `commitlint.base.js` / `.vscode/settings.json` / `*.code-workspace` 增量接线与去重。

    - 对外契约与模板根定位：
      `default_templates_dir` 按 `PENGJ_TEMPLATES` > `cwd/templates/` > 可执行文件旁 `templates/` 运行时定位；
      CLI 四命令 `list-layers` / `create` / `update` / `adopt` 与
      Tauri `invoke("cmd_*")` 6 命令的统一入口，
      渲染上下文 `RenderContext` 为跨 CLI/GUI 的唯一契约。

  - **本模块不负责（Out-of-Scope / 委托外部）**：

    - 业务模板内容本身：
      各层模板文件（`Cargo.toml` 具体依赖版本、`AGENTS.md` 领域规范细节、技能正文等）
      的业务语义与正确性由模板作者负责，
      引擎只负责按规则合并与渲染，不解释业务含义。

    - 前端 UI 细节：
      `crates/app/src` 的 React 组件树、Tailwind v4 样式、shadcn/ui 交互、Vite 打包、
      前端状态管理等由前端层自理；
      引擎仅通过 `crates/app/src-tauri/src/lib.rs` 的 `invoke` 契约暴露能力，
      不介入渲染与状态管理。

    - 用户项目的业务代码：
      生成后用户在目标仓库内编写的业务逻辑、自行引入的依赖与脚本、CI 配置等归用户所有；
      引擎仅在 `update_ignore` 声明的种子文件（如 `src/main.rs`）
      与受管块区间外保证“永不覆盖”，不接管业务演进。

## 2. 核心数据流与生命周期

### 核心数据流 / 调用时序

完整管线为 `resolve_layers → build_file_map → render_file_map → generate / adopt / update`，
所有分支共享前三步，仅落地策略不同：

```
用户输入（CLI args / GUI invoke payload）
  │
  ├─ Templates::new(root) / default_templates_dir() 定位模板根（见生命周期）
  │
  ▼
resolve_layers(selected: &[String]) -> Vec<String>  (engine.rs)
  │  读取全部 layer.toml → BTreeMap<id, LayerMeta>
  │  DFS visit 展开 depends，环检测 CircularDependency / 未知层 UnknownLayer
  │  输出按依赖顺序的 ordered 列表（先依赖后自身，已去重）
  │
  ▼
build_file_map(ordered, options) -> FileMap  (engine.rs)
  │  逐层 read_recursive 收集文件，跳过 layer.toml
  │  技能过滤：skill_name_of(rel) 命中 .agents/skills/<name>/… 时
  │            查 selected_skills(options)（缺失则全量，显式列表则白名单）
  │  三桶分流：
  │    ACCUMULATE_FILES(.gitignore/.gitattributes) → concat: Vec<(layer, bytes)>
  │    MERGE_JSON_FILES(package.json)              → json:   Vec<(layer, bytes)>
  │    其余                                      → normal: BTreeMap<rel, bytes>
  │                                                （后层覆盖前层）
  │
  ▼
render_file_map(fm, ctx, project_dir) -> BTreeMap<rel, Vec<u8>>
  │  (engine.rs + render.rs + context.rs)
  │  ctx = RenderContext::new(project_name, ordered, options)
  │       { project_slug = slugify(project_name),
  │         year = chrono_lite_year(), layers = ordered }
  │  normal:  render_bytes(bytes, ctx)
  │           → is_text ? render_text(minijinja) : 二进制直通
  │  concat:  各层片段分别 render → 取托管块 body（若有）
  │           → 按 "# --- <层> 层 ---" 拼接
  │           → 包入单一 "# PENGJ_TEMPLATE_START/END" 块
  │  json:    以磁盘既有文件为底（存在则用户优先）或空对象为底
  │           → 逐层 merge_json（依赖版本模板覆盖、脚本用户优先）
  │           → to_string_pretty 序列化
  │
  ├──────────────┬──────────────────┬──────────────────┐
  ▼              ▼                  ▼                  ▼
generate      adopt_project      update_project     list_layers
空目录写盘     存量纳管           增量同步           list_skills
                                               （只读查询）
```

三落地分支的判定与写盘规则：

- **generate（`crates/core/src/engine.rs::generate`）**：
  面向空目录（存在则必须为空，否则 `CoreError::DirExists`）。
  无磁盘冲突，直接 `write_file` 全部 `bytes_map`，
  计算 `sha256_hex` 写入
  `ProjectManifest { tool, version, project_name, layers: ordered, options, files }`
  并 `save` 到 `.pengj-templates.json`。

- **adopt_project（`crates/core/src/engine.rs::adopt_project`）**：
  面向已存在项目目录（已含 manifest 且非 `force` 则拒绝）。
  对 `bytes_map` 中每一项按优先级判定：

  - 命中 `collect_update_ignores` 黑名单 →
    仅当目标不存在时创建，否则完全跳过（不覆盖、不报冲突）；
  - `rel == .vscode/settings.json` →
    走 `sync_workspace_file` / `sync_settings_file` 增量合并
   （命中 `*.code-workspace` 时并入其 `settings` 节点）；
  - `json` 桶（`package.json`）→
    `bytes_map` 已以磁盘为底合并完成，直接写回；
  - `toml_merge::is_toml_managed`（`.cargo/config.toml`）→
    `merge_toml_managed(disk, incoming)` 表级并集 / 去重 / 冲突跳过；
  - 含受管块的 `normal`/`concat` 文本 →
    `merge_managed_block`（同风格 `Replaced`，无块 legacy `Appended`，
    技能主文档无块非空时 `take_over_legacy_skill` 接管——模板整页为准、原文下移过渡区）；
  - 无受管块或非文本 →
    仅记录 `sha256(bytes)` 作基线，不写盘
    （后续 `update` 靠 `disk_sha != recorded_sha` 触发冲突保护）。
  - `commitlint.base.js` 落地后尝试 `try_wire_commitlint_base` 自动接线
   （已接线 / 无 config / 需手工分别处理，去重等价条目）。

- **update_project（`crates/core/src/engine.rs::update_project`）**：
  `ProjectManifest::load` 读取基线 →
  `build_file_map` / `render_file_map` 重渲染
  （`options` 来自 manifest，原地复用生成时选项）→
  逐文件 `disk_sha` 与 `recorded_sha` 比对：

  - 磁盘未改（`disk_sha == recorded_sha`）→ 直接覆盖；
  - 磁盘已改且无受管块 →
    `conflicted`（`ConflictInfo { path, reason }`）跳过，不静默覆盖；
  - 磁盘已改且有受管块 →
    走受管块 / TOML / JSON 合并路径（同 adopt），
    `needs_review` 标注追加 / 接管类合并；
  - 模板新增文件 → `created`；
  - 模板已删除但本地仍存在 → `removed`（仅上报不删盘）。

- **list_layers / list_skills**：
  只读查询，不触发渲染管线；
  `list_skills` 对每个 `SKILL.md` 先按 `dummy_skill_ctx`（zh）渲染再解析 frontmatter `description`。

### 并发与上下文模型

- **单线程同步调用，无跨线程共享状态**：
  `pengj_core` 全量 API（`generate` / `adopt_project` / `update_project` / `Templates::*`）
  均为同步阻塞调用，内部仅使用 `std::fs` 与内存数据结构；
  无 `Arc` / `Mutex` / 线程池 / 异步运行时依赖。

- **CLI 上下文**：
  `crates/cli/src/main.rs` 的 `main` 单线程顺序执行 `load_templates → cmd_*`，
  `rayon` 等并发原语未引入；一次调用只处理一个项目目录。

- **GUI 上下文**：
  `crates/app/src-tauri/src/lib.rs` 的 6 个 `#[tauri::command]`
 （`cmd_list_layers` / `cmd_list_skills` / `cmd_create_project` /
  `cmd_update_project` / `cmd_adopt_project` / `cmd_list_workspaces`）
  由 Tauri 的 `async` invoke 层调度到后台线程，
  但每个命令内部对 `pengj_core` 的调用仍是同步的；
  命令间无共享可变状态，`Templates` 按调用即时构造，不跨调用缓存。

- **无后台任务与锁**：
  不需要文件锁或乐观并发控制；
  并发冲突的唯一协调点是 manifest 的 `sha256` 基线比对（乐观检测），
  检测到用户已改即跳过写盘并上报，由用户串行重跑 `update` 对齐。

### 生命周期

1. **初始化 — 模板根定位**：
   `default_templates_dir()` 按优先级
   `PENGJ_TEMPLATES` 环境变量 > `cwd/templates/`（开发态仓库根） >
   可执行文件旁 `templates/`（安装打包态）解析；
   CLI 的 `load_templates` 与 Tauri 的 `resolve_templates`
   （额外优先 `app.path().resource_dir()/templates`）均复用该策略。
   定位失败返回 `CoreError::TemplateRoot`，不回退到编译期嵌入。

2. **运行时读取 — 模板即文件系统**：
   所有模板内容运行时从磁盘 `templates/<layer>/` 递归读取，
   增删层或改文件无需重编译，改完直接 re-run 生效；
   `layer.toml` 与 `LAYER_META_FILE` 本身不写入目标项目。

3. **FileMap 渲染**：
   `build_file_map` → `render_file_map` 在内存完成全部合并与 minijinja 渲染，
   二进制文件按 `is_text`（前 8KB 无 NUL 即文本）直通，不经过模板引擎。

4. **磁盘写盘与 manifest 保存**：
   `write_file`（含 `create_dir_all`）落盘后，
   `ProjectManifest::save` 将 `layers` / `options` / `files: sha256`
   原子写入 `.pengj-templates.json`，作为后续同步的唯一基线。

5. **后续 update — 基线驱动同步**：
   每次 `update` 以 manifest 记录的 `sha256` 与当前磁盘 `sha256` 比对判定冲突；
   `options` 按 manifest 固化的值重渲染，
   保证同一项目多次同步使用同一 `edition` / `skill_lang` 等选项。

6. **热更新即重跑 update**：
   模板侧的任何变更（新增层、改受管块、调 `ACCUMULATE_FILES` / `MERGE_JSON_FILES` / `update_ignore`）
   无需重启服务，用户在已生成项目中重跑
   `pengj-templates-cli update --dir <project>` 或 GUI 的 `cmd_update_project`
   即完成同步；幂等——对同一模板版本连续两次 `update` 结果一致
   （TOML 合并 `normalize_tail` 与块替换均保证二次合并无漂移）。

## 4. 架构红线与禁止事项（Invariants & Anti-Patterns）

- **架构红线 1 — 模板运行时读取，不编译期嵌入**：
  `templates/` 目录在运行时按 `default_templates_dir` 定位并递归读取，
  增删层无需重编译；
  禁止把模板字节用 `include_str!` / `include_bytes!` 固化进二进制，
  否则违背“改模板直接 re-run 生效”的契约。

- **架构红线 2 — 后层覆盖前层，但累加与 JSON 例外**：
  同名普通文件以后层为准覆盖；
  `ACCUMULATE_FILES`（`.gitignore` / `.gitattributes`）必须累加拼接
  （每段带 `# --- <层> 层 ---` 注释、包入单一托管块），
  `MERGE_JSON_FILES`（`package.json`）必须结构化并集合并。
  禁止对这两类文件做简单覆盖。

- **架构红线 3 — 受管块区间外用户内容 100% 保留**：
  `PENGJ_TEMPLATE_START/END` 区间外的任何字节（用户自定义章节、块外配置）永不改动；
  有同风格块则仅替换区间，无块 legacy 文件追加到末尾并计入 `needs_review`，
  由用户复核而非自动去重。
  禁止整文件覆盖或丢弃块外内容。

- **架构红线 4 — TOML 同键异值必须冲突跳过，不静默覆盖**：
  `.cargo/config.toml` 的表级并集、键级去重中，
  同键不同值或“模板新键需并入用户已有同名表（TOML 禁止重复表头）”
  一律 `TomlMergeOutcome::Conflict` 且不写盘，
  逐条上报 `path: 用户值 / 模板值，请手工对齐后重跑 update`。
  禁止为通过而静默覆盖或产出非法重复表定义的 TOML。

- **架构红线 5 — JSON 依赖版本以模板为准，脚本以用户为准**：
  `package.json` 的 `dependencies` / `devDependencies` / `peerDependencies` / `optionalDependencies`
  同名包版本在 `generate` 与 `update`/`adopt` 时一律以模板为准
  （`overwrite_other || is_dep` 时 `insert` 覆盖）；
  `scripts` 同名键保留用户值（`or_insert`），其余字段模板仅补缺失。
  禁止颠倒优先级或对依赖做用户优先的保留。

- **架构红线 6 — manifest `sha256` 是唯一基线，不引入时间戳或文件大小判定**：
  `update` 的“未改即覆盖 / 已改即冲突”唯一依据是
  `ProjectManifest.files[rel]` 记录的 `sha256_hex` 与当前磁盘 `sha256` 的比对；
  禁止用 `mtime` / `file_size` 等弱信号替代，否则重命名后内容不变也会误判冲突。

- **架构红线 7 — 新增层只需加目录 + `layer.toml`，无需注册表**：
  `Templates::layer_metas` / `list_layers` / `resolve_layers` 均扫描
  `templates/` 直接子目录中带 `layer.toml` 的目录，目录名即层 `id`；
  禁止在代码中硬编码层白名单或维护额外注册文件。

- **架构红线 8 — `update_ignore` 黑名单文件仅首次生成**：
  `layer.toml` 的 `update_ignore` 声明的种子文件（如 `rust` 层的 `src/main.rs`）
  在 `generate` 后归用户所有，`adopt`/`update` 完全跳过（不覆盖、不报冲突、不删除上报）；
  禁止在更新路径中对黑名单文件做任何写盘或冲突判定。

- **架构红线 9 — `options` 固化后 `update` 必须原样重渲染**：
  生成时 `options`（`edition` / `channel` / `use_sccache` / `use_lld` /
  `chinese_programming` / `skill_lang` / `commit_zh` / `commit_and_push` / `skills`）
  随 manifest 持久化，`update` 按同一批 `options` 重渲染模板；
  禁止用当前 CLI 默认值覆盖已生成项目的选项。

- **架构红线 10 — 错误模型禁止裸 `unwrap` / `panic` 与 `as any` 逃生**：
  核心库公开 API 统一 `anyhow::Result` / `CoreError`（`thiserror`），
  磁盘读取失败 / UTF-8 非法 / TOML/JSON 解析失败均按 `Fresh` 回退或 `Conflict` 上报，不 `panic`；
  禁止引入 `as any` 式类型逃生。

- **常见反模式（Anti-Patterns）**：

  - 把业务逻辑写进引擎：
    如在 `engine.rs` 中为某模板的特定字段写 `if rel == "Cargo.toml"` 分支硬编码业务规则；
    应通过 `MERGE_JSON_FILES` / `toml_merge` / 受管块等通用机制处理，业务差异留在模板文件自身。

  - 硬编码层列表：
    在 `resolve_layers` 或 CLI 中写 `vec!["common","rust"]` 白名单；
    应始终从 `layer_metas` 动态发现，新增层零代码改动。

  - 静默覆盖已改文件：
    `update` 中对 `disk_sha != recorded_sha` 的文件直接 `write_file` 而不报 `conflicted`；
    正确做法是无受管块则冲突跳过，有受管块则走合并并 `needs_review`。

  - 重复表定义导致 TOML 非法：
    把模板受管块文本直接 `append_block` 到已含同名 `[target.*]` 的 `config.toml`，
    产出重复表头使 `cargo` 无法解析；
    必须走 `merge_toml_managed` 的结构化路径。

  - 编译期嵌入模板：
    用 `include_dir!` 打包 `templates/`；
    正确做法是运行时 `read_recursive`，保证运营期热更新语义。

  - 用 `mtime` 判定“是否被用户改过”：
    文件系统时间戳受拷贝/解压影响不可靠；唯一可信信号是 `sha256` 基线比对。

  - 在受管块外写模板应托管的表：
    如把项目可能自定义的 `[target.*]` 表写到 `.cargo/config.toml` 受管块之外，
    导致后续结构化合并误判冲突；
    模板里应把“由模板托管的表”全部放在受管块内，用户自定义表留在块外。

  - 忽略 `skills` 过滤：
    在 `build_file_map` 中未检查 `selected_skills` 即全量打包技能目录；
    应按 `skill_name_of` + `selected_skills` 白名单过滤，未选中技能整目录跳过。

  - 把用户选项当全局默认值：
    `update` 时用当前 CLI 的 `--edition 2024` 覆盖 manifest 中固化的 `edition`；
    正确做法是 `update` 完全以 manifest `options` 为准，CLI 默认值仅 `create`/`adopt` 生效。

  - 在 `MERGE_JSON_FILES` 之外手写 JSON 合并：
    对 `package.json` 以外的 JSON 文件也做并集；应仅对白名单内的文件走 `merge_json`，其余走普通覆盖或受管块。
