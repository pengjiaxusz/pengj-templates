# 模板支持子仓库与多工作树并行开发

> 本 spec 由 `/grill-with-docs` + `/to-spec` 产出。配套文档：[`GLOSSARY.md`](https://github.com/pengjiaxusz/pengj-templates/blob/main/GLOSSARY.md)、[`docs/adr/0001`](https://github.com/pengjiaxusz/pengj-templates/blob/main/docs/adr/0001-shared-build-dir-via-env-injection.md)、[`0002`](https://github.com/pengjiaxusz/pengj-templates/blob/main/docs/adr/0002-subrepo-and-worktree-as-separate-layers.md)、[`0003`](https://github.com/pengjiaxusz/pengj-templates/blob/main/docs/adr/0003-machine-readable-subrepo-registry.md)
>
> 实施工单见 [#133](https://github.com/pengjiaxusz/pengj-templates/issues/133) 的子 issue：#134（联动机制）→ #135（登记表）→ #136（体检）/ #137（技能改读）；#138（共享编译目录）→ #140（新建工作树）。

## 问题陈述（Problem Statement）

用 `pengj-templates` 生成的新项目，目前缺两块并行开发的基础能力。

**第一块是子仓库。** 项目依赖外部独立仓库（典型如 git submodule）时，模板没有提供任何「登记—校验—升级」的闭环：

- 子仓库同步技能虽然已经作为 `agent` 层的产物下发，但它要求项目自己维护一张 Markdown 表格。这张表格**不可被程序解析**——自检脚本与构建配方无法从中可靠地读取条目，格式一旦被调整，解析就失效，而且失效是静默的：检查「通过」了，实际什么都没查。
- 模板层没有为子仓库登记任何**机器可读的清单**，因此自检、配方、技能三方各说各话，没有单一事实源。
- 嵌套工作区这条红线——外部子仓库自带 `[workspace]` 定义时，若不被宿主工作区 `exclude`，Cargo 会把它的成员当作宿主工作区的 path 成员，导致 `*.workspace = true` 错误继承宿主的 `[workspace.package]`（缺 `rust-version` / `license` 等字段直接解析失败）——完全靠项目自觉，没有任何检查能发现它被违反。
- 子模块的「未初始化」状态，模板已有仓库初始化入口能补，但补完没有复核，项目无从知道当前是否真的就绪。

**第二块是多工作树共享编译产物。** 项目用多个 git 工作树并行开发时，每个工作树各持一份 `target`：

- 依赖被重复编译，重复消耗数十 GB 磁盘——这正是 `chahu-render-debugger` 当初要解决的问题。
- 项目要么自己发明方案（手工建 NTFS Junction），要么忍受重复开销。手工方案的问题在真实仓库里已经暴露：`chahu-render-debugger` 的现存工作树 `-a` 的 `target` **实测仍是独立物理目录**（`.rustc_info.json` 的大小与修改时间都与主仓不同），与它自己的设计文档不符；同一项目里两份文档还互相矛盾——`docs/开发规范/并行开发-worktree.md` 说共享主仓 `target`，而 `docs/architecture/01-上下文/进程架构.md:185` 仍写着「禁止共享主仓 `target/`」。
- 根本原因是：**链接状态无法被任何自动机制校验**。链接没建、被误删、或悄悄退化成独立目录时，没有任何环节会报警，只表现为「编译好像变慢了」。
- 与之相邻的另两件事也没解决：最终二进制在共享目录里路径固定，多个工作树会互相覆盖（`chahu-render-debugger` 靠自己的构建工具复制产物到各工作树的 `bin/` 来规避，但这是项目自有逻辑，模板不该也不该塞进去）；以及新开工作树时子模块不会自动补齐。

从用户视角看：**我勾了「并行开发」该有的那几项能力，但模板给不了我**；想要就得自己写脚本、自己记规矩、自己定期检查那些规矩有没有被违反。

## 解决方案（Solution）

给模板新增两个**独立可勾选**的层，各自闭环，互不依赖。

### `subrepo` 层 —— 子仓库登记与校验

- 产出一份**机器可读的登记表**（托管在模板产物目录下），逐条记录子仓库的名称、相对路径、依赖模式、上游跟踪分支与本地目录。表格是唯一事实源，技能、自检与配方都读它。
- 依赖模式是**枚举**而非自由文本，至少区分三类：git submodule 接入、由宿主构建系统按版本拉取（FetchContent 式）、本地同级目录。三类的升级与校验动作差别很大，模式必须是机器可读的。
- 自检环节覆盖两件今天没人查的事：**嵌套工作区红线**（登记了「自带工作区」标记的子仓库，若未出现在宿主工作区的排除清单里，报错并给出修复指引）与**子模块就绪状态**（指针漂移、未初始化）。
- 与已有的子仓库同步技能衔接：技能读同一份登记表，升级流程与影响面分析沿用现有实现，不重写。

### `worktree` 层 —— 多工作树共享编译产物

- 通过 **`CARGO_TARGET_DIR` 环境变量**注入仓库外的共享编译目录，由构建配方统一设置。共享目录的位置**按机器动态推导**（平台数据目录 + 项目标识），不是模板里的静态路径。
- 自检环节校验共享目录**存在、可写、当前指向正确**，并在修复模式下自动创建——这是手工链接方案根本不具备的能力。
- **产物覆盖**写进项目编码规范作为红线，并在自检里给出提示。共享目录只保证中间产物复用；最终产物的隔离是各项目的运行时形态，由项目自理。
- 新开工作树时顺带把子模块补齐——这件事今天仓库初始化入口已经能做，模板只需把它接进工作树配方。

### 共同约束

- 两层的产物一律落在模板产物目录下，不占用项目根的命名空间。
- 两层都只在被勾选时产出，不勾选就是零影响。
- 两层各自配套的技能自动带入（沿用现有「层 → 技能」的联动机制），避免「有配方没文档」的半接入。

## 用户故事（User Stories）

### 子仓库（subrepo 层）

1. 作为使用外部子仓库的项目维护者，我希望在模板生成时就能得到一份已填好说明的登记表，以便我知道该怎么登记子仓库，而不是自己从头设计格式。
2. 作为项目维护者，我希望登记表是机器可读的，以便自检脚本和构建配方能真正读到我登记的条目，而不是靠切分 Markdown 表格。
3. 作为项目维护者，我希望登记条目在模板更新后不被覆盖，以便我填的路径、模式、上游分支不会因为模板演进而丢失。
4. 作为项目维护者，我希望登记表里的说明随模板刷新，以便模板改进了登记方式时，我看到的用法说明不会停留在旧版本。
5. 作为项目维护者，我希望登记一个外部子仓库时能明确声明它的依赖模式，以便自检知道该对它做什么检查——子模块要查指针与就绪状态，构建系统拉取的要查版本锁定，本地目录的要查存在性。
6. 作为项目维护者，我希望自检能在我把自带工作区定义的外部仓库接入宿主工作区、却忘了把它排除掉时立刻报错，以便构建不会突然因为工作区继承解析失败而崩掉。
7. 作为项目维护者，我希望自检能告诉我该往宿主工作区的排除清单里加什么，以便我知道怎么修而不是只收到一句「配置有问题」。
8. 作为项目维护者，我希望自检能复核子模块是否真的初始化到位，以便我不必在构建失败后才想起来「忘了拉子模块」。
9. 作为项目维护者，我希望自检能指出子模块指针与登记的上游跟踪分支已经漂移，以便我及时发现本地在研改动与上游的偏离。
10. 作为项目维护者，我希望外部子仓库的升级流程仍然沿用我熟悉的那套技能与脚本，以便我不必为了用模板而重新学习一套升级方法论。
11. 作为项目维护者，我希望技能与自检读的是同一份登记表，以便技能建议的升级对象与自检检查的对象不会对不上。
12. 作为项目维护者，我希望不需要子仓库能力的项目完全不受影响，以便我不勾选这层时不会多出任何文件或检查。

### 多工作树（worktree 层）

13. 作为并行开发的项目维护者，我希望新工作树能与主仓共享一份编译产物目录，以便依赖只编译一次、磁盘不再被数十 GB 的重复产物撑爆。
14. 作为并行开发的项目维护者，我希望共享目录的位置按我的机器自动推导，以便它不依赖硬编码路径，我换台机器、换个盘符也不用改配置。
15. 作为并行开发的项目维护者，我希望自检能确认共享目录确实存在且可写，以便我不会在构建到一半才发现共享没生效、悄悄退回各自编译。
16. 作为并行开发的项目维护者，我希望自检在修复模式下能自动把共享目录建好，以便修复不需要我自己想命令。
17. 作为并行开发的项目维护者，我希望共享目录没生效时能立刻得到提示而不是「编译慢了一点」这种间接信号，以便我能确认并行开发的基础设施是好的。
18. 作为并行开发的项目维护者，我希望规范里明确写清「最终二进制在共享目录里会被各工作树互相覆盖」，以便我知道运行产物时该怎么隔离，而不是踩了坑才发现。
19. 作为并行开发的项目维护者，我希望模板不替我决定产物怎么隔离，以便不同项目的运行时形态（有的要复制动态库、有的根本不需要）不被一个通用实现绑住。
20. 作为并行开发的项目维护者，我希望新建工作树时子模块能自动补齐，以便新工作树开箱就能编译。
21. 作为并行开发的项目维护者，我希望这两个能力可以分别勾选，以便只想要其中一项的项目不必承担另一项的全部产物。
22. 作为项目维护者，我希望勾了工作树能力时相关的技能自动带上，以便我不会配出「有配方没文档」的半接入状态。

## 实现决策（Implementation Decisions）

### 层划分

- 新增 `subrepo` 与 `worktree` 两个层，`depends` 都只指向公共层与配方入口层。两者互不依赖（依据 [ADR-0002](https://github.com/pengjiaxusz/pengj-templates/blob/main/docs/adr/0002-subrepo-and-worktree-as-separate-layers.md)）。
- 层名 `worktree` 在说明文本里必须同时讲清两件事：工作树管理 **与** 共享编译目录。不能让使用者以为它只管前者。

### 子仓库登记（subrepo 层）

- **登记表为唯一事实源**，机器可读（依据 [ADR-0003](https://github.com/pengjiaxusz/pengj-templates/blob/main/docs/adr/0003-machine-readable-subrepo-registry.md)）。Markdown 表格降级为由配置派生的展示形式，不再是权威来源。
- 登记表放在模板产物目录下，遵循「模板产物一律落在标记目录下」的硬约定，不占用项目根的命名空间。
- 登记表形状 = **受管说明块 + 用户键值**：说明随模板刷新，用户填的条目永不覆盖。与提交门禁配置文件形状一致。
- **依赖模式是枚举**，至少三类：git submodule 接入 / 构建系统按版本拉取 / 本地同级目录。模式名本身是受管约束，不允许自由文本。
- 登记表需要能承载「该子仓库自带工作区定义」这个标记，否则嵌套工作区红线无法被自动检查。
- **不重写子仓库同步技能的升级流程与影响面分析**，只把它的输入从 Markdown 表格换成登记表。
- 层与技能的联动：勾 `subrepo` 层自动带上既有子仓库同步技能，沿用现有「层 → 技能」联动机制，在生成 / 纳管 / 更新 / 增量加层四个入口保持一致。

### 共享编译目录（worktree 层）

- **共享目录按机器动态推导**：平台数据目录 + 项目标识。平台数据目录的推导方式与更新检查的状态文件同源（Windows 用 LOCALAPPDATA，Unix 用 XDG_DATA_HOME）。不硬编码任何盘符或用户名。
- **注入点是构建配方**：由配方统一设置 `CARGO_TARGET_DIR`（依据 [ADR-0001](https://github.com/pengjiaxusz/pengj-templates/blob/main/docs/adr/0001-shared-build-dir-via-env-injection.md)）。
- **不在 Cargo 配置文件里写 `target-dir`**：该文件走模板的结构化合并，模板受管块与用户自定义区若各自出现同名表头会被判冲突、整文件不予写盘，用户配置会静默停在旧值。且共享目录路径本身需按机器推导，无法作为静态模板值落盘。
- **共享目录状态可被自检校验并自动修复**：存在性、可写性、当前指向。
- **产物覆盖写进规范红线 + 自检提示**，模板不实现产物隔离机制。理由：产物隔离是各项目的运行时形态（有的要复制动态库并以工作树为工作目录启动、有的不需要），通用实现反而会绑住项目。
- 共享目录下的**中间产物**复用由 Cargo 自身的指纹机制保证；模板不额外引入编译缓存包装器。

### 交汇点

- 新建工作树时补齐子模块，由**仓库初始化入口**承接（它已经负责工作区链接与子模块补齐），工作树配方调用它。子仓库层与工作树层各自独立调用该入口，互不调用对方。

### 通用约束

- 产物布局：一切模板产物落在模板产物目录下；根 `justfile` 与 `.githooks/` 仍是仅有的例外。
- 双语渲染：所有面向人的文案走 `skill_lang` 双语分支；中文分支的渲染结果必须与改动前逐字节一致。代码类产物用语言变体文件拆分。
- 受管说明块承载「会随行为演进的说明」，说明写在块外等于埋一条永不更新的假文案。
- 新增层必须进入现有覆盖全部层的双语端到端测试范围，否则文案漂移不会被门禁拦住。
- 自检脚本的检查项按层名条件启用，新增检查需在两套脚本（Unix / Windows）里同步；工具缺失的严重级别要与「该层是否为必需」一致。

### 迁移

- 本次为**新增能力**：不勾选新层的存量项目，渲染产物逐字节不变，无需迁移提示。
- 若后续需要改动 `templates/just/justfile` 的条件 import 装配区，那是存量项目也会看到的变更，须按破坏性变更处理并补迁移表条目。

## 测试决策（Testing Decisions）

### 好测试的标准

只测外部可观察行为：生成产物后读文件内容、断言其存在与关键内容；不测内部实现细节，不镜像引擎的内部结构。断言以「产物里有没有这段信息」为准，不以「函数返回了什么」为准。

### 测试接缝（复用现有，不新建）

现有测试全部内联在源文件的 `mod tests` 里（`crates/core` 与 `crates/cli` 都没有 `tests/` 目录），没有快照测试库、没有任何 dev-dependencies。因此**复用内联测试模块**，不引入新的测试依赖。

主接缝是引擎的端到端测试模块：它已经具备「定位真实模板目录 → 生成到临时目录 → 读回产物断言」的完整套路，且已有多个同类先例——层产物存在性与反向断言（不勾选时产物不存在）、层联动断言（依赖自动补齐）、跨层累加拼接断言。

### 具体测试项

1. **子仓库层产物存在性与反向断言**：勾选该层时，登记表与配方模块存在；不勾选时，两者都不存在。这是「新增层」最核心的断言形状，照现有先例写。
2. **登记表形状**：生成的登记表含受管说明块，说明部分随模板演进刷新；用户填的条目在更新后原样保留（值冻结、说明刷新）。
3. **依赖模式枚举**：登记的每个模式都被自检认识；出现未知模式时自检报错而不是静默跳过。
4. **嵌套工作区红线**：登记了「自带工作区」标记且宿主工作区未排除时，自检报错并给出修复指引；排除后通过。
5. **子模块就绪**：未初始化的子模块被检出；指针漂移被检出。
6. **层 → 技能联动**：勾选子仓库层时，对应技能自动进入选中集合；**四个入口一致**（生成 / 纳管 / 更新 / 增量加层）；审计对半接入给出非阻断提示。这条要照现有联动测试的形状写。
7. **共享编译目录推导**：共享目录路径由平台数据目录 + 项目标识推导得出，不含盘符、用户名等机器相关字面量；在两种平台语言设置下都能推出非空路径。
8. **共享目录不写进 Cargo 配置文件**：勾选工作树层后，生成的 Cargo 配置文件里**不含** `target-dir`；这是「避免结构化合并冲突」这条决策的回归防线。
9. **自检可修复共享目录**：修复模式下共享目录被创建；非修复模式下缺失即报错不创建。沿用仓库初始化入口已有的「只补缺、不覆盖」不变式。
10. **双语门禁覆盖**：两个新层进入现有覆盖全部层的双语端到端测试范围，让 `i18n_audit` 的双向门禁把住新层文案。
11. **层独立性**：只勾一个层时，另一个层的产物与检查项都不出现。

### 测试先例参考

- 层产物存在性与反向断言、层联动断言、跨层累加拼接断言：引擎测试模块内的现有用例。
- 结构化合并的冲突 / 去重 / 兄弟子表不冲突：合并模块的现有用例（该模块是 crate 私有，外部集成测试无法直接调用，新层若涉及其行为需在同文件内联测）。
- 「只补缺、不覆盖真实目录」的不变式：仓库初始化模块的现有用例。
- 破坏性变更的迁移表结构校验（版本可解析、严格升序、字段非空）：迁移模块的现有用例。

## 范围之外（Out of Scope）

- **实现产物隔离机制**。共享编译目录只保证中间产物复用；最终二进制跨工作树互相覆盖的风险由规范红线与自检提示承接，具体隔离方案由各项目自理。
- **引入编译缓存包装器**（sccache 一类）。Windows 命令行长度上限问题尚未解决，且它只解决依赖编译、不解决磁盘占用。
- **共享目录支持跨机器共享**（网络盘、分布式缓存）。只做单机多工作树。
- **重写子仓库升级方法论**。影响面聚类分析、指针祖先判定等沿用现有实现。
- **为子仓库实现通用的依赖版本协商**。上游 API 破坏性变更的适配仍是项目侧工作。
- **修改现有项目的既有共享方案**。存量项目若已自建 Junction 或环境变量方案，本次不迁移、不接管。
- **子模块的递归嵌套治理**。递归初始化交给 Git 自带能力，模板只做就绪性检查。
- **工作树之外的并行形态**（克隆、分布式开发）。只覆盖 git 工作树。

## 补充说明（Further Notes）

### 现状快照（2026-11-18）

`chahu-render-debugger` 是这套能力的现实原型，其当前状态值得记录，因为它是「为什么不能照抄」的最佳论据：

- **共享编译目录靠手工建 NTFS Junction**，命令写在项目自己的开发规范文档里，没有任何脚本、`doctor --fix` 也不覆盖它。实测现存工作树 `-a` 的 `target` 仍是独立物理目录——**方案已静默退化**。
- 同一项目的两份文档对「是否共享主仓 target」互相矛盾。
- 最终产物隔离靠项目自有的构建工具复制到各工作树的 `bin/`，并以工作树为工作目录启动；同时项目根解析改用 git 命令而非可执行文件位置，以避免共享产物下的路径误指。这部分**不适合进通用层**。
- 外部 UI 引擎仓库以 git submodule 形式接入，被宿主工作区排除后以 path 依赖方式消费；升级流程用「拉取未应用提交 + 聚类影响面 + 一键签出」三段式，本地指针还长期停留在功能分支上，与登记的上游分支漂移。

### 与既有能力的边界

- **仓库初始化入口**（子模块补缺、工作区链接、仓库级 Git 配置）与模板层无关，它操作的是机器上的仓库状态；新层只是调用它，不复刻它的逻辑。
- **子仓库同步技能**已作为 `agent` 层产物下发，新层不新增技能文件，只把它接上机器可读的登记表。
- **排队层**管的是「同一台机器上多个工作树别把 CPU 吃满」，本层管的是「多个工作树别重复编译依赖」。两者正交，可同时勾选。

### 命名注意

层名 `subrepo` 与既有技能名 `subrepo-sync` 不重名，但同处一个仓库时容易混淆。层的说明文本需点明二者关系：层提供登记与校验的基础设施，技能提供升级方法论。
