# 共享编译目录落在主工作树的 `target/`

ADR 0001 定了「用 `CARGO_TARGET_DIR` 注入」这个机制，但把落点定在**仓库外**：平台数据目录 + 项目标识哈希。机制没变，落点要改——共享目录改成**主工作树的 `target/`**。

## Status

accepted（部分取代 ADR 0001 的落点结论；注入机制、不写 `.cargo/config.toml` 两条仍然有效）

## Why

平台数据目录这个落点在实践中露出五个问题，前三个是日常摩擦，后两个是功能性缺陷：

- **产物与项目分居两块盘**：项目在 D/E 盘，产物却在 C 盘用户目录。本机 C 盘余量本来就紧，三个仓库的共享目录就占了 5.2G，且会随仓库数线性增长；而项目所在的盘反而有空间。
- **清理边界说不清**：「清理这个项目的产物」要记住两个位置——项目内的 `target/`（已无人写入，只剩死重）和平台数据目录下的桶。`cargo clean` 清的是前者，等于没清。
- **按项目看不见**：磁盘告警时无法从项目目录一眼看出它占了多少，得先去平台数据目录按哈希找桶。
- **主工作树裸构建不命中**：共享目录在仓库外时，主工作树里直接 `cargo build` 会写自己的 `target/`，只有经配方才复用。共享从「默认行为」退化成「记得用配方」。
- **按 `./target/<cfg>` 定位产物的项目直接用不了**：`chahu-render-debugger` 的 xtask 全程读项目内 `target/<cfg>`，落点在仓库外时连主工作树的打包链都读不到产物。

## Considered Options

- **平台数据目录 + 项目哈希**（原方案）：上面五条即其问题。它对「多仓库零散小项目」还算合适，但对我们这种「少数大仓库、每仓多工作树」的形态是本末倒置——真正需要复用产物的是同一个仓库的多个工作树，而这个关系 git 自己就知道。
- **主工作树同级的兄弟目录**（`…/repo.target`）：`cargo clean` 不会误伤，但多出一个「藏在项目旁边、和项目同辈分」的目录要维护；项目整体搬走时容易漏掉它，心智上也不是「项目的产物」。
- **目录链接**：已在 ADR 0001 否决（状态无法被校验，退化是静默的），不重开。
- **主工作树的 `target/`**（采纳）：零新增目录、`.gitignore` 早已覆盖、主工作树裸构建天然命中、项目整体搬迁与备份都把它当自己的一部分。判定主工作树靠 `git worktree list --porcelain` 的第一条——git 自己维护这个事实，不需要我们发明项目标识。

## Consequences

- **`cargo clean` 变成仓库级操作**：在主工作树里跑它（或 `git clean -xdf`）会删掉所有工作树的中间产物，每个都得全量重建（实测量级：本仓 ~13s 冷编译、`dunting` 约 2 分钟、`unbound-ui` 约 6 分钟）。这条必须写进技能、配方注释与本页，不能只留在提交信息里。
- **最终产物覆盖关系不变**：共享目录里路径固定，并行工作树互相覆盖；区别只是主工作树自己的构建现在也参与覆盖。隔离仍归项目自理。
- **项目标识与自己分桶的哈希退役**：主工作树本身就是桶，Cargo 自己按 profile / target 分目录，不再需要三元组子目录。
- **非 git 目录退回自身 `target/`**：单目录项目没有「别的工作树」可分，这是正确结果而不是降级。
- **迁移**：平台数据目录下的旧 `shared-target/` 是纯编译产物，确认各仓都换新版 CLI 后可直接删除，不需要逐桶甄别。
- 一个边界仍然存在：链接工作树里的**裸** `cargo build`（不经配方）仍会写自己的 `target/`。这条与 ADR 0001 一致，靠配方注入与 `wt-check` 承接。
