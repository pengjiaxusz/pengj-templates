# 子仓库登记表用机器可读格式，不再只靠 Markdown 表格

子仓库同步技能目前要求项目维护一张 Markdown 表格，逐条登记子仓库的名称、相对路径、依赖模式与上游跟踪分支。模板要让自检、配方与技能三方共用同一份清单。

我们决定让登记表成为**机器可读的结构化配置**（托管在模板产物目录下），Markdown 表格降级为可选的展示形式。

## Status

accepted

## Considered Options

- **保持 Markdown 表格为唯一来源**：技能读起来最自然，但自检脚本与配方要从中解析表格，必须依赖脆弱的文本切分；表格格式一旦被用户调整，解析随即失效，且失效方式是静默的——检查「通过」了，实际什么都没查。
- **结构化配置为唯一来源，表格由配置派生**：自检与配方读配置，技能读配置并在需要时渲染出表格。代价是表格不再能承载「为什么这个子仓库存在」这类散文说明，因此这些说明改放在技能文档与项目文档里，而不是硬塞进表格单元格。

## Consequences

- 登记表是**受管说明块 + 用户键值**的形状：说明随模板刷新，用户填的条目不被覆盖。与提交门禁的配置文件形状一致。
- 登记表本身位于模板产物目录之下，遵循「模板产物一律落在标记目录下」这条约定，不占用项目根的命名空间。
- 依赖模式需要枚举定义：至少区分「以子模块形式接入」「由宿主构建系统按版本拉取」「本地同级目录」三类。这三类的升级与校验动作差别很大，用自由文本写模式名会让自检无法判断该做什么。
- 嵌套工作区这条红线（外部子仓库自带工作区定义时，必须被宿主工作区排除，否则工作区继承关系解析失败）需要机器可读的登记信息才能被自检覆盖——这正是表格方案做不到的部分。
