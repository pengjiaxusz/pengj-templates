# 共享编译目录用 CARGO_TARGET_DIR 注入，不用目录链接

多个 git 工作树并行开发时，各自持有一份编译产物目录会重复占用数十 GB 磁盘、重复编译第三方依赖。需要在多工作树间共享同一份编译产物目录。

我们选择**通过 `CARGO_TARGET_DIR` 环境变量注入仓库外的共享目录**，由构建配方统一设置，而不是把工作树的 `target` 做成指向共享目录的目录链接。

## Status

accepted

## Considered Options

- **目录链接**（Windows NTFS Junction / Unix 符号链接）：Cargo 完全无感、相对路径天然成立。但它只能在「主仓目录名硬编码在链接目标里」时工作，路径随目录改名而失效；更关键的是**链接状态无法被任何自动机制校验**——链接没建、被误删或悄悄退化成独立目录时，没有任何环节会报警，只会表现为「编译变慢了」。`chahu-render-debugger` 就正处在这个状态：现存工作树的 `target` 实测仍是独立物理目录，与设计文档不符。
- **在 `.cargo/config.toml` 写 `[build] target-dir`**：这是 Cargo 的官方位置，但该文件走模板的结构化合并。模板受管块与用户自定义区若各自出现 `[build]` 表头，同表头路径重合会被判为冲突，**整个文件不予写盘**——用户的构建配置会因此静默停留在旧值。共享目录本身也需要按机器与项目动态推导，无法作为静态模板值落盘。
- **编译缓存包装器**（sccache 一类）：按内容哈希跨目录共享，但 Windows 上存在命令行长度上限这一长期未解问题，且它只缓存依赖编译、不解决磁盘占用。

## Consequences

- 共享目录的位置必须**按机器动态推导**（平台数据目录 + 项目标识），不能是模板里的静态路径。
- 注入发生在**构建配方**这一层，因此只有经由配方发起的构建才享受共享；直接手敲编译命令会退回各自独立的产物目录。这个边界必须写进文档，不能靠使用者记忆。
- 共享目录的状态（存在、可写、当前指向）**可被自检环节校验并自动修复**，这正是目录链接方案缺失的能力。
- 最终二进制路径固定，多个工作树仍会互相覆盖。共享目录只保证**中间产物**复用；产物隔离属于各项目自己的运行时形态，由项目自理。
