Lesson 03 · 反馈闭环与人的位置

让评审收敛，把人留在哪里

最后一个概念块：评审者本身也会出错、会绕圈；团队用事故和人的行为训练它，同时把判断权明确留给人。

约 7 分钟 · 4 题自测 · 收束全篇

01评审必须收敛，否则会互相喂养

作者是 agent 时，噪声更贵：人可以几秒忽略一个 nit，agent 却会真的去改——于是多一个 commit，再多一轮评审。作者与评审者都是 agent 时，可以无限互相触发。原文举了一个 CLI PR：作者叫停前一晚跑了 50 多轮。

团队用 git blame 查评审者反复标记的内容，发现约 59% 是从评审者第一次评审起就存在的旧代码——它不是在发现新 bug，而是每轮多翻出一点旧的。

他们意识到：是自己把流程训练成了「默认跑几轮」，因为每轮总能抓到点新东西。

于是加了四条收敛规则：

  • 轮数上限：3 轮后请作者退后一步重审方案，而不是继续抠细节。
  • 前几轮之后只复审新 diff，不全文重扫。
  • 标注 bug 的类别，让作者一次修掉所有同类，而不是改一行。
  • 不重复已发表过的发现。

同时把「轮数」和召回率一起追踪。细节见 参考手册 · 让评审收敛。

02评审者怎么变好：事故即 eval

团队把过去引发事故的 PR、对应的修复与回滚收集起来，请熟悉那块代码的工程师逐条确认 bug 与位置，做成评测集。评审者每天跑一遍；它的每次改动都要对全套重新打分。

光看召回率会诱导误报，所以团队还用人的行为测噪声：按人对每条评论的处理分类——修了 / 说不对 / 说有意如此 / 说无所谓；并在已知干净的 PR 上跑，数「会导致有害改动」的误报次数。

写下来的优先级

先抓真 bug，再减少评审轮数。顺序反了，就会得到一个安静但漏东西的评审者。

漏审时团队问的不是「提示词怎么写得更好」，而是「模型当时没看到什么」，把答案写进 CLAUDE.md、skill 或新检查。评审 agent 还每晚扫现有代码，提前抓旧 bug。

03人留在哪里

把「读代码」交给机器之后，人不是退场，而是移到只有人能判断的位置：

  • 要不要做——方向、品味、范围。有团队即便宣称评审瓶颈已解，仍对来自团队外的改动保留人工评审，只为问一句「我们该做这件事吗」。
  • 高风险代码——计费、自动更新器、CI workflow。
  • 架构——会别人照抄的模式。
  • 读证据——测试输出、实际命令与返回值、截图、评审发现。说不出检查会漏什么时，要的是真评审，不是快批。
  • 承担结果——每个上线的改动都有人负责，不论谁敲的键盘。

原文还给了两个配套规范：「你落地，你负责」——中小改动出问题，落地者通常自己修；以及知识传播——不再指望谁有完整心智模型，想理解某块代码就让 Claude 生成针对那一切片的 explainer 或可视化小产物。

04先回忆，再看答案

不看上文，说出让评审收敛的四条规则。
①三轮上限，之后请作者重审方案；②前几轮后只复审新 diff；③按 bug 类别一次修全；④不重复已发表的发现。
「事故即 eval」和「用人的行为测噪声」分别解决什么问题？
前者用历史事故组成每日评测集，衡量评审者抓真 bug 的能力；后者按人如何处理评论、以及在干净 PR 上的误报，衡量噪声。两者一起防止「多报即变好」的假象。

05自测：收束全篇

06全文的一句话收束

目标没有变：每次改动花更少的人工时间，且不比从前更多的回滚。

文章把这条线画到——对外产品只提交发现、不提交批准；他们自己的仓库走得更远，让 owner 决定哪些低风险改动仅凭自动检查合并，并且这条线还在往前移。同时坦白：还没有「指标恶化就自动收紧审批」的断路器，工程师希望在更多代码走向零人工合并之前先有它。

保留判断把这些当成一套有自报数据支撑、仍在演进的工程实践，而不是已被独立验证的行业定律。这正是第一课的护栏思路在「读这篇文章」上的应用。
