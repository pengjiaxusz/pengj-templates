Lesson 01 · 核心重构

评审到底在评什么

这节课只解决一个问题：为什么「有没有人读过代码」是个坏问题，以及团队用什么取代了它。

约 6 分钟 · 4 题自测 · 学完你能用自己的话讲清评审的新目标

01先看规模

Anthropic 的 monorepo 里，每天合并的改动从 5 月的约 2,500 个涨到 9 月的 30,000 多个。同期 Claude Code 仓库合并的 PR 翻倍以上，而被回滚的 PR 占比反而下降超过 40%。

原文开头还说，Claude Code 自身约 90% 的代码由 Claude 编写。在这种产出速度下，要求每个人逐行读完每个 diff，不 just 困难，而是几乎不可能。

先别急着下结论这组数字来自团队自报，没有独立复现。它们的作用是设定问题规模，不是证明方法正确。方法好不好，要看后面的指标设计与事故闭环。

02核心重构：换个问题问

评审一直干两件事：①上线前发现并修复问题；②让团队共享对代码库的理解。这篇文章主要谈第一件。

团队的判断是：「有没有人读过代码？」是一个不精确的代理。真正该问的是——

这次改动可能出什么错？哪一道检查——自动的或人工的——适合拦住它？

问题一换，评审的时机也变了：不再是流程末端那道「写完 → 开 PR → 等同同事」的闸门，而是像拼写检查一样持续发生。大多数改动在被人看到之前，已经被 Claude 至少评审并修过一轮。

术语锁定

后文凡说「评审」，默认指发现并修复问题这一职责；谈知识传播时会明确说「第二个职责」。术语对照见 参考手册 · 术语表。

03稀缺资源：人的时间与注意力

人的时间出现在成本的两侧：评审花掉的时间，以及修坏代码花掉的时间。只砍前者，省下的时间会原封不动出现在后者——那不叫省，叫搬。

所以团队的优化目标写成了一句可检验的话：

大多数 PR 在最多一个人的参与下合并——这个人可以是作者——且不抬高回滚率与事故率。

类别指标读法
成本（要降）每 PR 人工审批数（中位数 / P95）、人工评论数、PR 等人的时长省下了多少人时
护栏（不许坏）回滚率、事故率证明成本不是被转移到事后

完整定义见 参考手册 · 成本指标与护栏指标。这组「目标 + 护栏」的写法，是整篇文章最值得带走的一件东西。

04先回忆，再看答案

合上页面想 10 秒：「有没有人读过代码」为什么是个坏问题？团队改问什么？
它衡量的是手段（读没读），不是目的（会不会出错、谁拦得住）。改问：「这次改动可能出什么错，哪一道检查适合拦住它。」
如果只把评审时间压到零，却让回滚率上升，按文章的口径算成功吗？为什么？
不算。回滚率与事故率是护栏指标：上升就说明省下的人工时间只是转移到了事后修复，没有真正节省。

05自测：确认你真的带走了它

先选，再看反馈。题目考的是理解，不是记忆原句。

06这节课的锚点

  • 评审 = 发现并修复问题 + 传播理解；本文主线是前者。
  • 坏问题：「有没有人读过？」；好问题：「可能出什么错，谁拦得住？」
  • 评审从末端闸门变成持续过程，像拼写检查。
  • 成本指标要降，护栏指标（回滚 / 事故）不许坏。

下一课沿着「谁拦得住」往下走：一次改动从作者机器到用户，究竟穿过哪七层关卡，以及哪些层能直接挡住合并。见 第二课：一次改动的七层关卡。
