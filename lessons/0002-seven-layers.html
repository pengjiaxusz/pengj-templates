Lesson 02 · 机制拆解

一次改动的七层关卡

把「谁拦得住」拆开：从作者的机器到用户，改动穿过七层；每层拦一部分、漏一部分，少数穿过全部，剩下的交给回滚。

约 7 分钟 · 4 题自测 · 承接第一课的成本 / 护栏框架

01先记住这张地图

关键心智模型：不是一道闸门，而是层层过滤 + 事后兜底。越靠前的层越便宜、越机械；越靠后的层越贵、越需要人的判断。

层做什么谁能挡
1 自验证测试 / 构建 / 截图对比；新上下文 subagent 复审常规错误（PR 之前）
2 AI 评审读 diff + 全仓 + PR 意图；多 agent 并行、投票去噪发现必须回应，未清不能合并
3 安全评审独立一轮发现未清，硬挡合并
4 自动检查lint / 类型 / 多平台测试 / 构建机械回归，硬挡
5 人工审批按风险分级：0 / 1 / 2 人只有人能判断的部分
6 合并队列在主干上重跑全部检查；功能开关；渐进发布两个 PR 各自通过却合坏主干
7 发现与回滚遥测、内部先用、每周 on-call、一键回滚漏网的错，事后兜底

逐层细节可查 参考手册 · 七层关卡；这节课只讲最容易误读的三处。

02第一层：让机器先跑，让人看证据

提交前给 Claude 一个能判定成败的检查——测试、构建、和设计稿对比的截图——并要求它展示输出，而不是口头说「做完了」。然后用一个全新上下文的 subagent 复审 diff。

评审者反复标记同一类问题时，团队不在评论里反复说，而是在源头修：写进 skill、加 lint 规则、或更新说明文件。这是把一次性意见沉淀成永久检查。

关键判断

「展示证据」比「声称完成」便宜得多：读测试输出、命令返回值、截图，比自己重跑一遍快。人看的是证据，不是承诺。

03第二层：AI 评审怎么不被噪声淹没

研究预览上线后，内部 PR 收到实质性评审意见的比例从 16% 升到 54%；千行以上的 PR 大多有发现，小改动大多干净通过。但「多报」很容易变成噪声，所以团队加了几道阀：

  • 并行 + 投票：多个 agent 同时找 bug，另一组对每条发现投票，够多认可才发布。
  • 丢弃低价值类：只涉及风格、诊断、清理的发现直接扔掉，这些过滤在内部 PR 上做过 A/B 测试。
  • 标注性质：Important / Nit / Pre-existing；最后一种明确告诉作者「这不是你引入的」。
  • 每条必须有回复：要么修，要么说明理由关闭。agent 常常连夜把发现修掉，作者第二天看到的是已经过了一轮的 PR。

按仓库设 Quick / Standard / Deep 三档；原文的判断标准很实用：漏掉一个 bug 的代价比多花的评审时间更高时，才值得开 Deep。

04第五层：风险分级，四条容易看错的规则

低风险（文档、文案、开关后的内部功能）在自动检查全绿后无需人工；中风险（普通产品改动、缓存、自动更新器、系统提示词）要一人；高风险要两人。

真正容易看错的是这四条：

  1. 改动定级，不是作者定级。分类器读改动内容选档；第二个分类器再问「这次是否额外需要一个人」。
  2. 只有可信作者走轻量通道。其他人都需要第二人批准。
  3. agent 的批准不算人的批准。自动评审能清掉低风险改动，但填不了「必须有人」的那个名额。
  4. 谁驱动 agent，谁占一个名额；批准只覆盖当时的 commit。出现 agent 推送或手工解决的合并冲突，批准要重新给。

完整表格见 参考手册 · 风险分级。

05先回忆，再看答案

把七层按顺序列一遍——列到几层算几层，别翻上面的表。
①提交前自验证 + 新上下文复审；②每个 PR 的 AI 评审；③可阻塞的安全评审；④阻塞式自动检查；⑤按风险分级的人工审批；⑥合并队列 + 功能开关 + 渐进发布；⑦快速发现与回滚。
为什么「agent 批准了」不能算作那个需要的人类审批？
因为人类审批是为了让只有人能判断的部分有人负责；自动评审可以清掉低风险改动，但不能填「必须有人」的名额。在 agent 写的 PR 上，驱动 agent 的人算一个评审者，等于亲自写的那种责任。

06自测：机制是否真的清楚了

07这节课的锚点

  • 七层是过滤器 + 兜底，不是一道闸门。
  • 验证先于评审：给机器可判定的检查、看证据，再让新上下文 agent 复审。
  • AI 评审靠并行投票、丢弃风格类、标注性质、每条必回，来控制噪声。
  • 审批按改动的风险分级；agent 的批准永远不算人的批准。

下一课处理最容易被忽略的问题：评审者本身也会出错、会绕圈。见 第三课：让评审收敛，把人留在哪里。
